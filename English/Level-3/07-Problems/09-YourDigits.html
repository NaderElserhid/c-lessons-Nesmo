Your Digits

A small greedy problem that teaches an important lesson: sometimes there seem to be several ways to allocate a limited resource, but setting your priorities correctly (highest value first) always guarantees the best possible outcome.

Medium Codeforces 734B (Anton and Digits)

Problem Statement

You have k2 copies of the digit 2, k3 copies of 3, k5 copies of 5, and k6 copies of 6. You want to form as many of the numbers 32 and 256 as possible using these digits (each individual digit is used at most once), such that the sum of all the formed numbers is as large as possible.

Each 256 needs one digit each of 2, 5, 6. Each 32 needs one digit each of 3, 2. Unused digits don't count toward the sum.

Constraints

  • 0 ≤ k2, k3, k5, k6 ≤ 5×10⁶

Official Examples (Verified)

k2 k3 k5 k6ResultExplanation
5 1 3 48003 copies of 256 (using 3 of k2, all of k5, 3 of k6) + one 32 (using the last remaining 2 and the 3) = 256×3+32 = 800
1 1 1 1256Only one 256 (uses up all the digits), leaving no 2 left to make a 32

The Solution Idea: Priority to the Higher-Value Number

  • 256 > 32 by a large margin. So we should always form as many 256s as possible first, before considering 32.

  • The number of times we can form 256 is limited by whichever of the three required digits is scarcest: k = min(k2, k5, k6).

  • After spending k copies of digit 2 on making 256s, we're left with only k2 - k copies of 2 to make 32s.

  • The number of times we can form 32 with what's left is limited by min(k3, k2 - k).

  • Final total: k × 256 + min(k3, k2-k) × 32.

Why is this ordering always correct? Every digit 2 we spend on 256 instead of 32 might "cost" us the chance for one 32 (worth just 32), but it earns us an entire 256 in exchange — and this trade is always a win (256 > 32) as long as the needed digits 5 and 6 are available. So there's never a scenario where we lose by giving 256 the highest priority.

The Full Solution

your_digits.cpp
#include <iostream>
#include <algorithm>
using namespace std;

int main() {
    int k2, k3, k5, k6;
    cin >> k2 >> k3 >> k5 >> k6;

    int k = min(min(k2, k5), k6);

    int solution = k * 256 + min(k3, k2 - k) * 32;
    cout << solution << '\n';
}

We verified this manually against both official examples: (5,1,3,4) → k=min(5,3,4)=3 → 3×256 + min(1, 5-3)×32 = 768+32 = 800. And (1,1,1,1) → k=1 → 256 + min(1,0)×32 = 256. Both match the official outputs exactly.

Points Worth Watching

Greedy orderIf we reversed the priority (making 32s first before 256s), we might spend digits 2 that would have produced a more valuable 256 — reducing the final result.
Digit 2 is used by both256 and 32 both depend on digit 2, which is why we need to subtract k from k2 before computing the 32 share, rather than using the original k2 in both computations.
Numeric type rangeThe maximum possible sum here is 5×10⁶×256 ≈ 1.28×10⁹, which fits within standard int capacity (~2.1×10⁹), but is close to it; it's good practice to always check the maximum possible value before assuming int is sufficient.

A correct greedy algorithm is often built on an "exchange argument": proving that choosing the higher-value option first can never be worse than any other ordering, because the maximum possible loss (a missed opportunity for a smaller number) is always less than the guaranteed gain (the larger number itself).
