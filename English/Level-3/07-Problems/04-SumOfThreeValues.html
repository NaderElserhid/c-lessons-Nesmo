Sum of Three Values

A natural extension of the previous Sum of Two Values problem: instead of a map answering one membership question, this time we'll fix two elements and search for the third with binary search inside a sorted array — because this problem's constraints (a much smaller n) allow for a slightly higher complexity.

Medium CSES 1641 — Sorting and Searching

Problem Statement

You're given an array of n integers, and you need to find three different positions whose three values sum to a target number x given beforehand.

If more than one valid triple exists, you may print any of them. If no triple satisfies the condition, print IMPOSSIBLE.

Constraints

  • 1 ≤ n ≤ 5000

  • 1 ≤ x, aᵢ ≤ 10⁹

Notice the difference from the previous problem: here n ≤ 5000 only (not 2·10⁵ as in Sum of Two Values) — a strong hint that the expected solution has a higher complexity than O(n log n), specifically something close to O(n² log n).

Input

First line: two integers n and x — the array size and the target sum.
Second line: n integers representing the array values.

Output

Either three positions (1-indexed) whose three values sum to x and are all different from each other, or the word IMPOSSIBLE if no valid triple exists.

Example

Input: 4 8 2 7 5 1 Output: 1 3 4

Check: a[1] + a[3] + a[4] = 2 + 5 + 1 = 8. Correct.

Any order is acceptable: the CSES judge only checks that the sum is correct, not that the numbers or order match the official example exactly — so our algorithm may output a different valid triple (or in a different order) and be accepted just the same. You'll actually see this in the lab below.

How Do We Build On the Previous Problem's Idea?

  • The first naive solution: check every possible triple with three nested loops — complexity O(n³). With n = 5000, that's about 1.25×10¹¹ operations — far too slow.

  • Notice the similarity to the previous problem: if we fix one element a[i], what's required from the rest becomes exactly "find a pair that sums to x - a[i]" — which is exactly the Sum of Two Values problem!

  • But the solution here chooses to fix two elements instead of one: instead of reusing a map for each value of i (which is also possible), we fix i and j together, then search for the third value need = x - a[i] - a[j] with a direct binary search — this requires sorting the array first (while keeping the original positions).

  • Why does sorting allow binary search? After sorting, the values become ascending, so we can check whether a specific value exists within a given range in O(log n) time instead of scanning it fully.

  • Why do we only search in [j+1, n-1]? To guarantee the third element comes after j (in the sorted array), so the three positions are always automatically distinct, exactly as we did earlier by searching the map before inserting.

Bonus — an alternative approach: this problem can also be solved by fixing just one element i, then using two pointers moving from both ends of the range [i+1, n-1] toward each other in O(n) time per i — giving a total complexity of O(n²), faster than the binary search approach explained here. Both approaches are correct and accepted by the judge.

Complexity Analysis

  • Sorting: O(n log n) just once at the start.

  • The nested loops i, j: at most O(n²) pairs.

  • For each pair, one binary search: O(log n).

Total time = O(n² log n)

For n = 5000: roughly 5000² × log&sub2;(5000) ≈ 25,000,000 × 13 ≈ 3.25×10⁸ operations — comfortably accepted within the one-second time limit. Pay close attention: if this problem's constraints were n ≤ 2·10⁵ (as in Sum of Two Values), this approach would be far too slow — the relatively small constraint (5000) is precisely what allows us to use a quadratic complexity here in the first place.

The Full Solution

sum_of_three_values.cpp
#include <algorithm>
#include <iostream>
#include <vector>
using namespace std;

int main() {
    ios::sync_with_stdio(false);
    cin.tie(nullptr);

    int n;
    long long x;
    cin >> n >> x;

    vector<pair<long long, int>> a(n);
    for (int i = 0; i < n; ++i) {
        long long v;
        cin >> v;
        a[i] = {v, i + 1};  // the value with its original position (1-based)
    }

    sort(a.begin(), a.end());  // sort by value

    // fix two elements (i, j) and binary search for the third
    for (int i = 0; i < n; ++i) {
        for (int j = i + 1; j < n; ++j) {
            long long need = x - a[i].first - a[j].first;

            int lo = j + 1, hi = n - 1;
            while (lo <= hi) {
                int mid = (lo + hi) / 2;
                if (a[mid].first == need) {
                    // found a valid triple
                    cout << a[i].second << " "
                        << a[j].second << " "
                        << a[mid].second << "\n";
                    return 0;
                } else if (a[mid].first < need) {
                    lo = mid + 1;
                } else {
                    hi = mid - 1;
                }
            }
        }
    }

    cout << "IMPOSSIBLE\n";
    return 0;
}

We verified this code manually against the official example: after sorting, the array becomes [(1,4), (2,1), (5,3), (7,2)], and the first triple the code actually finds is at i=0, j=1 (values 1 and 2), giving need = 8-1-2 = 5, and the binary search in [2,3] finds the value 5 at mid=2 — so the code prints 4 1 3. This is different in form from the official example's output 1 3 4, but is equally correct (the same triple, in a different order) — which is exactly expected given the problem statement itself.

Points Worth Watching

Integer overflow — a real risk this time: unlike Sum of Two Values where there was no real overflow risk, here need = x - a[i] - a[j] subtracts two values that can each reach 10⁹ from a value that can also reach 10⁹ — and the total sum (if computed differently) could approach 3×10⁹, which exceeds the capacity of an int (32-bit, maximum roughly 2.1×10⁹). So using long long for both x and the array values is mandatory here, not just a safety habit as in the previous problem.

Uniqueness of the three positionsGuaranteed automatically because the binary search is always restricted to the range [j+1, n-1] — i.e. always after j, and therefore after i too.
Saving the original position before sortingYou must store each value along with its original (1-based) index before sorting, otherwise you'll lose track of the real position you need to print.
n limits differ from the previous problemn ≤ 5000 here only, not 2·10⁵ — don't automatically assume the same constraints as a previous problem apply to a new one, and always tie the allowed complexity to the given size of n.
Finding no solutionYou must finish checking every possible pair (and the binary search for each) before concluding there's no solution and printing IMPOSSIBLE.

Notice the natural progression across this series: Sum of Two Values introduced us to the idea of "fix one element and search for the rest through a fast data structure," and Sum of Three Values extended the same idea by one more level of nesting. So don't be surprised if a following "Sum of Four Values" problem builds on the same philosophy, often by combining the hashing idea from the first problem with the double-fixing idea from this one.
