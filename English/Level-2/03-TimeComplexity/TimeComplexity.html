Time Complexity

You've now learned two powerful STL containers: set and map. But how do you know that the solution you wrote will be fast enough? In this chapter you'll learn how to "measure" the speed of any algorithm without actually running it, and how to predict in advance whether your solution will get Accepted or Time Limit Exceeded when submitted on Codeforces — exactly the skill you'll need for the rest of your competitive programming journey.

What is time complexity?

When we write programs, some solutions run faster than others. Time Complexity is a way to measure how quickly the number of steps an algorithm takes grows as the input size grows.

We don't measure it in seconds (because that depends on the machine's speed), but instead we measure it by the number of steps that increases as the input size increases. This lets us compare algorithms with each other without actually needing to run them.

basic_loop.cpp
for (int i = 0; i < n; i++)
    cout << i << " ";

If n = 10, the code prints 10 numbers. If n = 1000, it prints 1000 numbers. If n doubles, the number of steps doubles too.

We say this code runs in O(n) time, because it takes roughly n steps. This means the time grows linearly with the input size.

What does Big O mean?

The symbol O (Big O) shows how the number of steps an algorithm takes grows as n increases. We only care about the dominant growth term, not about constants or small details — for example 2n + 5 and n are both written as O(n).

ExampleComplexityDescription
x = a + b; or if/elseO(1)Constant time — runs instantly regardless of the size of n
set::insertO(log n)Each step roughly cuts the problem size in half
A single loop over an arrayO(n)The time grows linearly
SortingO(n log n)A bit slower than O(n), but much faster than O(n²)
Two nested loopsO(n²)The time grows very quickly as n increases
Trying every possible combinationO(2ⁿ)Exponential growth — increases enormously fast

Counting Steps: Practical Examples

The best way to understand Big O is to actually count the steps inside the code. Note that simple arithmetic operations (+ - * / % ^), increment/decrement (++ --), compound assignments (+= -= *= /=), and if/else statements are all counted as a single constant-time step O(1).

1) A single loop → O(n)

one_loop.cpp
long long sum = 0;                    // 1 step
for (int i = 1; i <= n; i++)          // n times
    sum = sum + i;                    // constant step each time

Number of steps ≈ 1 + n → we drop the constant 1 → O(n). To verify: n·(n+1)/2 gives the same result as the loop (for n=5: 5·6/2 = 15 = 1+2+3+4+5), but this direct formula is computed in a single step, O(1) — another example of the "improving solutions" we'll see later.

2) Two nested loops → O(n²)

two_loops.cpp
for (int i = 0; i < n; i++)           // n times
    cout << i;
for (int j = 0; j < n; j++)           // n times
    for (int k = 0; k < n; k++)       // n times for each j → n² total
        cout << j + k;

Number of steps ≈ n + n² → the dominant term is n² → O(n²).

3) Adding a third nested loop → O(n³)

three_loops.cpp
for (int j = 0; j < n; j++)
    for (int k = 0; k < n; k++)
        for (int l = 0; l < n; l++)   // n × n × n = n³
            cout << j + k + l;

By adding a third nested loop, the number of steps becomes n³, so the complexity becomes O(n³) — much slower than O(n²).

4) A doubling loop → O(log n)

doubling_loop.cpp
for (int i = 1; i < n; i = i * 2)      // i doubles each time
    cout << i;

Since i doubles every time (1, 2, 4, 8, ...), the number of iterations needed to reach n is roughly log₂(n), so the complexity is O(log n).

5) Nested loops with doubling → O(n log²n)

nested_log.cpp
for (int i = n / 2; i < n; i++)         // ≈ n times
    for (int k = 1; k < n; k = k * 2)    // log n times
        for (int j = 1; j < n; j = j * 2) // log n times
            cout << i + k + j;

The result: n · log n · log n = O(n log²n).

6) Two regular loops and a doubling loop → O(n² log n)

two_plus_log.cpp
for (int i = 0; i < n; i++)             // n times
    for (int j = 0; j < n; j++)         // n times
        for (int k = 1; k < n; k = k * 2) // log n times
            cout << i + j + k;

The result: n · n · log n = O(n² log n).

7) A regular loop and a division loop → O(n log n)

divide_loop.cpp
for (int i = 0; i < n; i++)             // n times
    for (int j = n; j > 1; j = j / 3)   // log₃n times ≈ O(log n)
        cout << i + j;

Dividing by any constant number (2 or 3 or otherwise) gives the same order of growth O(log n) (only the base changes, which is a detail we ignore). The result: n · log n = O(n log n).

Best, Average, and Worst Case

The speed of the same algorithm can vary depending on the shape of the input. That's why we distinguish between three cases, each with its own mathematical symbol:

CaseSymbolMeaning
Best CaseΩ (Omega)The smallest possible number of steps on the best possible input
Average CaseΘ (Theta)The expected number of steps on a typical random input
Worst CaseO (Big O)The largest possible number of steps on the worst possible input

Let's apply this to Linear Search: we go through the array elements one by one looking for a specific value, and stop as soon as we find it.

Worked Examples

Example 1: Incrementing a Number — Constant Time O(1)

You are given a number x. Increase x by 1, then print it.

increment.cpp
#include <iostream>
using namespace std;

int main() {
    int x;
    cin >> x;
    x += 1;
    cout << x << '\n';
}
Input: 7 → Output: 8

We did three simple operations: read, increment, and print. All of them are constant-time operations — we don't say this is O(3) because we don't care about constants; we only care about the dominant growth. So this is O(1).

Example 2: Sum of Money — Linear Time O(n)

You are given n bills worth arr[0] riyals, arr[1] riyals, ..., arr[n-1] riyals. What is the total number of riyals you have?

money_sum.cpp
#include <iostream>
using namespace std;

int main() {
    int n;
    cin >> n;
    int arr[n];
    for (int i = 0; i < n; i++)
        cin >> arr[i];

    long long sum = 0;
    for (int i = 0; i < n; i++)
        sum += arr[i];

    cout << sum << '\n';
}
Input: 4 / 10 20 30 40 → Output: 100

The first loop (reading) runs n times, and the second (summing) also runs n times. In total: n + n = 2n, but we ignore constants, so the complexity is O(n) — if the array doubles, the time doubles too.

Example 3: Copies — Quadratic Time O(n²)

You are given n bills. For each of n days, increase the value of every bill by one, and print the values of all the bills for each day.

copies.cpp
#include <iostream>
using namespace std;

int main() {
    int n;
    cin >> n;
    int arr[n];
    for (int i = 0; i < n; i++)
        cin >> arr[i];

    for (int days = 1; days <= n; days++) {
        for (int i = 0; i < n; i++) {
            cout << arr[i] + days << ' ';
        }
        cout << '\n';
    }
}
Input: 3 / 1 2 3 Output: 2 3 4 3 4 5 4 5 6

There are n days, and on each day we go through n bills, so the total is n · n = n² operations. If n = 100, the number of steps = 10,000. If n = 1000, the number of steps = 1,000,000. That's why O(n²) algorithms can become very slow, very quickly.

A Quick Rule of Thumb

You'll recall from the "Contests and Platforms" chapter that every problem has a time limit (usually one or two seconds), and that a processor can execute roughly 10⁸ operations per second. This gives us a handy rule of thumb for guessing the appropriate kind of solution based on the size of n in the problem:

Maximum acceptable complexityn
O(n!)≤ 10
O(2ⁿ) usually acceptable≤ 20
O(n²) usually acceptable≤ 1000
O(n log n) or better≤ 10⁵
O(n) or better≤ 10⁷
Only O(log n) or O(1)≥ 10⁹

This helps you guess the appropriate type of solution for a given input size even before you start writing code. For example, if you see N ≤ 3000 in a problem (as in the Iso-celestial problem), you know in advance that a solution with O(N²) complexity will be acceptable, while O(N³) will be far too slow.

Improving Solutions

Sometimes it isn't obvious, but you can make a program faster by thinking of smarter solutions.

The Simple Sum

You are given a number n. Find the sum: -n + (-n+1) + (-n+2) + ... + -1 + 0 + 1 + ... + (n-2) + (n-1) + n.

A simple solution (linear O(n)):

simple_sum_naive.cpp
#include <iostream>
using namespace std;

int main() {
    int n;
    cin >> n;
    long long sum = 0;
    for (int i = -n; i <= n; i++)
        sum += i;
    cout << sum << '\n';
}
Input: 5 → Output: 0

This solution runs in O(n) time.

A smarter solution (constant O(1)):

We can do better than that. Every number appears once positive and once negative — i and -i — so each pair cancels the other out, and only zero (0) remains in the middle. The simplest solution:

simple_sum_smart.cpp
#include <iostream>
using namespace std;

int main() {
    int n;
    cin >> n;
    cout << 0 << '\n';
}
Input: 5 → Output: 0

This solution is O(1), constant time and much faster than the simple solution. In practice, when testing both solutions with a huge value like n = 300{,}000{,}000, the linear solution took about 0.19 seconds, while the constant solution took less than 0.002 seconds — a huge difference even though both give the same correct answer! Always try to think of the fastest possible solution.

Space Complexity

Sometimes we also care about how much memory a program uses. This is called space complexity. It's exactly the same idea: how does memory usage grow as the input size grows?

space_example.cpp
int arr[n];  // O(n) space — grows with the input size
int x;       // O(1) space — constant regardless of n

There's often a trade-off between time and memory: sometimes you can make a solution faster by using extra memory (as we did with a set to remove duplicates), and sometimes the opposite is true.

Homework Exercises

1) Determine the Time Complexity of the Following Code

hw1.cpp
for (int i = 0; i < n; i++)
    for (int j = i; j < n; j++)
        cout << i + j;

Notice that the inner loop doesn't start from zero, but from i. What is the complexity of this code?

The number of times the inner loop runs decreases with each value of i: when i=0 it runs n times, when i=1 it runs n-1 times, and so on down to once. The total is n + (n-1) + ... + 1 = n(n+1)/2.

Even though the exact formula is n(n+1)/2, its dominant term is n², so the complexity remains O(n²) — still quadratic even though the actual number of operations is roughly half of two full loops.

2) Determine the Time Complexity of the Following Code

hw2.cpp
int lo = 0, hi = n;
while (lo < hi) {
    int mid = (lo + hi) / 2;
    if (arr[mid] < target) lo = mid + 1;
    else hi = mid;
}

This is Binary Search, which we studied earlier. What is its time complexity?

In each iteration, the range [lo, hi) is roughly cut in half. This is exactly like the doubling loop we studied, but in the opposite direction (shrinking instead of growing). The number of splits needed to go from n down to a single element is log₂(n), so the complexity is O(log n) — which is why binary search is much faster than linear search on a large, sorted array.

Input: array [1,3,5,7,9,11], target=7 → Found at index 3

3) Improve the Solution from O(n²) to O(n)

You have an array, and you need to check whether it contains two elements whose sum equals a given target value. The following naive solution uses two nested loops with O(n²) complexity. Rewrite it using a set so the complexity becomes roughly O(n) (make use of what you learned in the first chapter of this level!).

two_sum_naive.cpp — O(n²)
bool found = false;
for (int i = 0; i < n && !found; i++)
    for (int j = i + 1; j < n && !found; j++)
        if (arr[i] + arr[j] == target) found = true;
two_sum_smart.cpp — roughly O(n)
#include <iostream>
#include <set>
using namespace std;

int main() {
    int n, target;
    cin >> n >> target;
    int arr[n];
    for (int i = 0; i < n; i++) cin >> arr[i];

    set<int> seen;
    bool found = false;
    for (int i = 0; i < n; i++) {
        if (seen.count(target - arr[i])) { found = true; break; }
        seen.insert(arr[i]);
    }

    cout << (found ? "Yes" : "No");
}
Input: 4 9 / 2 7 11 15 → Yes (2 + 7 = 9) Input: 4 100 / 1 2 3 4 → No

For each element, we check in O(log n) whether its "complement" (target - arr[i]) has appeared previously in the set. Since the loop runs n times and each set operation costs O(log n), the total complexity is O(n log n) — much faster than the original O(n²) when n is large.
