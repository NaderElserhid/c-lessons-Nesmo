Debugging

Finding and Fixing Bugs Quickly and Smartly

What Is Debugging?

It's very common, when solving a problem, for your program to not behave exactly as you expected. The process of discovering what went wrong and fixing it is called Debugging.

There's no single "perfect" way to debug a program, but there are techniques that help you find the bug faster instead of reading the code line by line with no plan. In this chapter we'll go over the most important of these techniques: writing clean code from the start, using cout to trace values, using assert to catch logical errors automatically, plus a comprehensive list of practical tips.

Code Style

Cleaner code is less likely to contain bugs in the first place. Make sure to name your variables clearly so you don't mix them up, and use consistent indentation and spacing to improve readability when you debug later.

Example: Bad Code

bad.cpp
#include <iostream>
#include <cmath>
#include <cassert>
#include <iomanip>
#include <algorithm>
using namespace std;
int main() {
int a, b;
cin >> a >> b;
int n[a];
for (int m=a-1; m>-1; m-=1) {
cin >> n[m];
}
    cout << n[b]; }

Example: Good Code

good.cpp
#include <iostream>
using namespace std;

int main() {
    int n, m;
    cin >> n >> m;

    int a[n];

    for (int i = n - 1; i >= 0; i--) {   // inputting the array from right to left
        cin >> a[i];
    }

    cout << a[m];
}
  • Only include (#include) the libraries you actually need, and don't use massive templates you don't need.
  • Use n and m to express sizes or counts — this is the convention in most programming problems, which makes your code easier to read and understand.
  • Use i, j, and k as loop variable names — these are common standard names inside loops.
  • Keep consistent indentation: each nesting level should be shifted by one tab (or 4 spaces).
  • Remove the indentation when closing any block — this helps you visually spot where a loop or condition ends.
  • Leave comments when needed to clarify what you intended to do, and compare it to what you actually did.

Printing

The idea is to use cout to trace the values of our variables. If we notice that a variable holds an unexpected value, that can give us a clue as to why the bug is happening.

Suppose we're trying to print an array in reverse order:

reverse_v1.cpp
int a[5] = {1, 2, 3, 4, 5};

for (int i = 4; i >= 0; i++) {
    cout << a[i] << ' ';
}
Output: 5 0 -1150222592 1577706123 1165962832 32767 126...

This doesn't look right... let's print the value of i before every print to see which index is actually being printed.

reverse_v2.cpp
int a[5] = {1, 2, 3, 4, 5};

for (int i = 4; i >= 0; i++) {
    cout << "index 'i' is: " << i << '\n';
    cout << a[i] << '\n';  // change this to \n to make the output more readable
}
Output: index 'i' is: 4 5 index 'i' is: 5 0 index 'i' is: 6 1781710592 index 'i' is: 7 1056066187...

We expect the value of i to be 4, 3, 2, 1, 0 but instead it's increasing. The update expression for i is the increment expression in the for-loop. It should be i--, but instead it's i++, and that was the bug.

reverse_fixed.cpp
int a[5] = {1, 2, 3, 4, 5};

for (int i = 4; i >= 0; i--) {
    cout << a[i] << ' ';
}
Output: 5 4 3 2 1

Assert

The assert function takes a boolean expression as its argument, and if that expression evaluates to false, the program stops immediately. On most online judges, this stop results in a Runtime Error verdict. This is very useful when a program has several branches and produces a different verdict we can't explain.

To use this function you must include the cassert library.

For example, suppose we have a problem that says: given an integer n, compute 1 + 2 + ... + n.

fast_only.cpp
#include <iostream>
using namespace std;

int fast(int n) {
    return n * (n + 1) / 2;
}

int main() {
    int n;
    cin >> n;
    cout << fast(n);
}

Submitting this program gives us Wrong Answer. We might have another, slower solution that we're more confident is correct — like a loop that adds up the values one by one. In that case, we can use assert to check that the slow solution (slow) and the fast solution (fast) produce the same value:

with_assert.cpp
#include <iostream>
#include <cassert>

using namespace std;

int slow(int n) {
    int ans = 0;
    for (int i = 1; i <= n; i++) ans += i;
    return ans;
}

int fast(int n) {
    return n * (n + 1) / 2;
}

int main() {
    int n;
    cin >> n;

    assert(fast(n) == slow(n));

    cout << fast(n);
}

This has two possible outcomes: either we get Time Limit Exceeded, which means we're likely passing the small tests (and the mathematical formula is correct), or we get Runtime Error because the assert failed, meaning the two solutions produce different results.

If we get a Runtime Error we can review the formula and confirm its correctness, whereas if we get Time Limit Exceeded we can conclude that the formula fails on large numbers, which most likely means an Overflow issue (the type's capacity being exceeded).

Additional Tips

Output and Formatting

  • Make sure the output format matches the problem statement exactly (no extra spaces or lines).
  • Remove all debug prints before submitting.

Input and Edge Cases

  • Handle all edge cases (such as N = 0, N = 1, empty input, maximum limits).
  • In problems with multiple test cases, reset all variables and containers between each test.
  • Bugs often show up when a small test comes right after a large one.

Reviewing the Problem and the Code

  • Re-read the problem statement carefully.
  • Re-read your code — common mistakes: mixing up N/M, i/j, etc.
  • Watch out for shadowed, unused, or uninitialized variables.

Undefined Behavior

  • Uninitialized variables.
  • Out-of-bounds access on an array/vector.
  • Forgetting return in a non-void function.
  • Signed integer overflow — use long long.
  • Bit-shifting by ≥ 32 on 32-bit numbers.

Floating Point

  • Check for NaN values (such as sqrt of a negative number).
  • Use long double for extra precision when needed.
  • Match the required output precision using setprecision().

Testing

  • Do a manual walkthrough on simple cases.
  • Stress test: compare your fast solution's results against a slow, reliable brute-force solution.

Runtime Error

  • Is there any undefined behavior?
  • Are there assertions that might fail?
  • Is there a possible division by zero? (or mod 0)
  • Is there a possible infinite recursion?
  • Invalid pointers or iterators?
  • Are you using more memory than necessary?

Time Limit Exceeded

  • Are there any possible infinite loops?
  • What is your algorithm's time complexity?
  • Did you remove debug output before submitting (like heavy printing to stderr)?
  • Is there unnecessary copying of data? Consider passing variables by reference.
  • Try replacing vectors with plain arrays.

Last Resort

  • Rewrite your solution from scratch.
  • Make sure to keep a copy of your original solution — it's always possible to introduce new bugs into your new solution.

Glossary of Terms

DebuggingBug fixing

The process of discovering why a program behaves unexpectedly and fixing it.

AssertionA required check

A condition that must be true; if it isn't, the program stops immediately (assert).

Undefined BehaviorUnspecified outcome

A situation whose outcome C++ doesn't precisely define, such as accessing outside an array's bounds.

OverflowCapacity exceeded

A variable's value exceeding the maximum its type can store.

Stress TestingRandomized comparison

Comparing a fast solution to a slow, reliable one on many random inputs to find a discrepancy.

Edge CaseA boundary input

An unusual input (like zero or maximum values) that might expose a flaw in the logic.

Runtime ErrorCrash during execution

The program stopping abnormally while running, such as a failed assert or division by zero.

Time Limit ExceededToo slow

The solution is logically correct but slower than the allowed time limit.
