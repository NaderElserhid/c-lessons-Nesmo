التصحيح (Debugging)

إيجاد الأخطاء وإصلاحها بسرعة وذكاء

ما هو التصحيح؟

من الشائع جدًا عند حل مسألة أن لا يتصرّف برنامجك تمامًا كما توقعت. عملية اكتشاف ما الذي حدث خطأً وإصلاحه تُسمّى التصحيح (Debugging).

لا توجد طريقة واحدة "مثالية" لتصحيح برنامج، لكن توجد تقنيات تساعدك على إيجاد الخطأ بسرعة أكبر بدلًا من قراءة الكود سطرًا سطرًا بلا خطة. في هذا الفصل سنستعرض أهم هذه التقنيات: كتابة كود نظيف من البداية، استخدام cout لتتبّع القيم، استخدام assert لاكتشاف الأخطاء المنطقية تلقائيًا، بالإضافة إلى قائمة شاملة من النصائح العملية.

أسلوب كتابة الكود (Code Style)

الكود الأنظف أقلّ عرضة لاحتواء أخطاء من الأساس. تأكّد من تسمية متغيّراتك بشكل واضح حتى لا تخلط بينها، واستخدم مسافات بادئة (indentation) وتباعدًا منتظمًا لتحسين قابلية القراءة عند التصحيح لاحقًا.

مثال: كود سيئ

bad.cpp
#include <iostream>
#include <cmath>
#include <cassert>
#include <iomanip>
#include <algorithm>
using namespace std;
int main() {
int a, b;
cin >> a >> b;
int n[a];
for (int m=a-1; m>-1; m-=1) {
cin >> n[m];
}
    cout << n[b]; }

مثال: كود جيد

good.cpp
#include <iostream>
using namespace std;

int main() {
    int n, m;
    cin >> n >> m;

    int a[n];

    for (int i = n - 1; i >= 0; i--) {   // inputting the array from right to left
        cin >> a[i];
    }

    cout << a[m];
}
  • ضمّن فقط المكتبات (#include) التي تحتاجها فعليًا، ولا تستخدم قوالب ضخمة (massive templates) لا داعي لها.
  • استخدم n و m للتعبير عن الأحجام أو العدّادات — هذا هو المتعارف عليه في أغلب مسائل البرمجة، مما يجعل كودك أسهل للقراءة والفهم.
  • استخدم i و j و k كأسماء لمتغيّرات التكرار (loop) — هذه أسماء قياسية شائعة داخل الحلقات.
  • حافظ على مسافة بادئة ثابتة: كل مستوى تعشيش (nesting) يجب أن يُزاح بمقدار تاب واحد (أو 4 مسافات).
  • أزل الإزاحة عند إغلاق أي كتلة (block) — هذا يساعدك على تمييز مكان انتهاء الحلقة أو الشرط بصريًا.
  • اترك تعليقات عند الحاجة لتوضيح ما كنت تنوي فعله، ومقارنته بما فعلته فعليًا.

الطباعة (Printing)

الفكرة هي استخدام cout لتتبّع قيم متغيّراتنا. إذا لاحظنا أن متغيّرًا يحمل قيمة غير متوقعة، فقد يعطينا ذلك دليلًا على سبب حدوث الخطأ.

لنفترض أننا نحاول طباعة مصفوفة بترتيب معكوس:

reverse_v1.cpp
int a[5] = {1, 2, 3, 4, 5};

for (int i = 4; i >= 0; i++) {
    cout << a[i] << ' ';
}
Output: 5 0 -1150222592 1577706123 1165962832 32767 126...

هذا لا يبدو صحيحًا... لنطبع قيمة i قبل كل عملية طباعة لنرى ما هو الفهرس الذي تتم طباعته فعليًا.

reverse_v2.cpp
int a[5] = {1, 2, 3, 4, 5};

for (int i = 4; i >= 0; i++) {
    cout << "index 'i' is: " << i << '\n';
    cout << a[i] << '\n';  // change this to \n to make the output more readable
}
Output: index 'i' is: 4 5 index 'i' is: 5 0 index 'i' is: 6 1781710592 index 'i' is: 7 1056066187...

نتوقّع أن تكون قيمة i هي 4, 3, 2, 1, 0 لكنها بدلًا من ذلك في ازدياد. تعبير تحديث i هو تعبير الزيادة (increment expression) في حلقة الـ for. يجب أن يكون i-- لكنه بدلًا من ذلك i++، وهذا كان الخطأ.

reverse_fixed.cpp
int a[5] = {1, 2, 3, 4, 5};

for (int i = 4; i >= 0; i--) {
    cout << a[i] << ' ';
}
Output: 5 4 3 2 1

المختبر التفاعلي: تتبّع حلقة التكرار خطوة بخطوة

أدخل حجم المصفوفة، واختر اتجاه التحديث (i++ الخاطئ أو i-- الصحيح)، وشاهد كل خطوة فعلية للحلقة: هل الفهرس داخل حدود المصفوفة أم خارجها.

Assert

الدالة assert تقبل تعبيرًا منطقيًا (boolean expression) كمعامل، وإذا كانت قيمة هذا التعبير false فإن البرنامج يتوقف فورًا. في أغلب المُقيّمات الإلكترونية، هذا التوقف ينتج عنه الحكم Runtime Error. هذا مفيد جدًا عندما يحتوي البرنامج على عدة مسارات (branches) وينتج عنه حكم آخر لا نفهم سببه.

لاستخدام هذه الدالة يجب تضمين مكتبة cassert.

على سبيل المثال، لدينا مسألة تقول: بمعطى عدد صحيح n، احسب 1 + 2 + ... + n.

fast_only.cpp
#include <iostream>
using namespace std;

int fast(int n) {
    return n * (n + 1) / 2;
}

int main() {
    int n;
    cin >> n;
    cout << fast(n);
}

عند إرسال هذا البرنامج نحصل على Wrong Answer. قد يكون لدينا حل آخر أبطأ لكننا أكثر ثقة بصحته — مثل حلقة تكرارية تجمع القيم واحدة تلو الأخرى. عندها يمكننا استخدام assert للتحقق من أن الحل البطيء (slow) والحل السريع (fast) ينتجان نفس القيمة:

with_assert.cpp
#include <iostream>
#include <cassert>

using namespace std;

int slow(int n) {
    int ans = 0;
    for (int i = 1; i <= n; i++) ans += i;
    return ans;
}

int fast(int n) {
    return n * (n + 1) / 2;
}

int main() {
    int n;
    cin >> n;

    assert(fast(n) == slow(n));

    cout << fast(n);
}

لهذا نتيجتان محتملتان: إمّا أن نحصل على Time Limit Exceeded، مما يعني أننا على الأرجح ننجح في الاختبارات الصغيرة (والصيغة الرياضية صحيحة)، أو نحصل على Runtime Error بسبب فشل الـ assert، مما يعني أن الحلّين ينتجان نتائج مختلفة.

إذا حصلنا على Runtime Error يمكننا مراجعة الصيغة والتأكد من صحّتها، أما إذا حصلنا على Time Limit Exceeded فيمكننا استنتاج أن الصيغة تفشل على الأعداد الكبيرة، مما يعني على الأرجح مشكلة Overflow (تجاوز سعة النوع).

المختبر التفاعلي: قارن الحل البطيء بالحل السريع باستخدام assert

أدخل قيمة n وشاهد slow(n) و fast(n) يُحسبان فعليًا في المتصفح، ثم راقب نتيجة الـ assert. يمكنك أيضًا "كسر" الصيغة السريعة عمدًا لترى كيف يبدو فشل الـ assert.

نصائح إضافية

الإخراج والتنسيق

  • تأكّد من أن تنسيق الإخراج يطابق نص المسألة تمامًا (بدون مسافات أو أسطر زائدة).
  • أزل جميع مخرجات التصحيح (debug prints) قبل الإرسال.

الإدخال والحالات الحدّية

  • عالج جميع الحالات الحدّية (مثل N = 0، N = 1، إدخال فارغ، الحدود القصوى).
  • في المسائل متعددة الاختبارات، أعد ضبط جميع المتغيّرات والحاويات بين كل اختبار.
  • غالبًا ما تظهر الأخطاء عندما يأتي اختبار صغير بعد اختبار كبير.

مراجعة المسألة والكود

  • أعد قراءة نص المسألة بعناية.
  • أعد قراءة كودك — الأخطاء الشائعة: الخلط بين N/M، i/j، إلخ.
  • انتبه للمتغيّرات المُظلَّلة (shadowed)، غير المستخدَمة، أو غير المُهيّأة (uninitialized).

السلوك غير المُعرَّف (Undefined Behavior)

  • متغيّرات غير مُهيّأة (uninitialized).
  • الوصول خارج حدود المصفوفة/المتّجه (out-of-bounds).
  • نسيان return في دالة غير void.
  • تجاوز سعة الأعداد الصحيحة الموقّعة (signed overflow) — استخدم long long.
  • إزاحة بتّية (bit-shifting) بمقدار ≥ 32 على أعداد 32-بت.

الأعداد العشرية (Floating Point)

  • تحقّق من قيم NaN (مثل sqrt لعدد سالب).
  • استخدم long double لدقّة إضافية عند الحاجة.
  • طابق الدقّة المطلوبة في الإخراج باستخدام setprecision().

الاختبار (Testing)

  • نفّذ تتبّعًا يدويًا (manual walkthrough) على حالات بسيطة.
  • اختبر بضغط (stress test): قارن نتائج حلّك السريع بحلّ بطيء وموثوق (brute-force).

Runtime Error

  • هل يوجد سلوك غير معرَّف؟
  • هل توجد assertions قد تفشل؟
  • هل يوجد احتمال قسمة على صفر؟ (أو mod 0)
  • هل يوجد احتمال استدعاء ذاتي (recursion) لا نهائي؟
  • مؤشّرات (pointers) أو مكرّرات (iterators) غير صالحة؟
  • هل تستهلك ذاكرة أكبر من اللازم؟

Time Limit Exceeded

  • هل توجد حلقات لا نهائية محتملة؟
  • ما هي التعقيد الزمني (complexity) لخوارزميتك؟
  • هل أزلت مخرجات التصحيح قبل الإرسال (مثل الطباعة الكثيرة إلى stderr)؟
  • هل يوجد نسخ غير ضروري للبيانات؟ فكّر بتمرير المتغيّرات بالمرجع (by reference).
  • جرّب استبدال المتّجهات (vectors) بمصفوفات عادية (arrays).

الملاذ الأخير

  • أعد كتابة حلّك من الصفر.
  • احرص على حفظ نسخة من حلّك الأصلي — من الممكن دائمًا أن تُدخل أخطاءً جديدة في حلّك الجديد.

تحقق من فهمك

١. ما هي أفضل طريقة لتصحيح أي برنامج؟

توجد طريقة واحدة "مثالية" يجب اتّباعها دائمًا
لا توجد طريقة واحدة "مثالية"، لكن توجد تقنيات تساعد على إيجاد الخطأ بشكل أسرع
إعادة كتابة البرنامج بالكامل هي الحل الوحيد دائمًا

٢. لماذا يُعتبر كتابة كود نظيف ومنظّم جزءًا من التصحيح؟

لأن الكود الأنظف أقلّ عرضة لإنتاج أخطاء، ويسهّل ملاحظة الأخطاء عند حدوثها
لأنه يجعل البرنامج يعمل أسرع تلقائيًا
لا علاقة بينهما إطلاقًا

٣. في مثال طباعة المصفوفة بترتيب معكوس، ما كان الخطأ الفعلي؟

القيمة الابتدائية لِـ i كانت خاطئة
تعبير تحديث الحلقة كان i++ بدلًا من i--
حجم المصفوفة كان خاطئًا

٤. ما وظيفة الدالة assert؟

تتحقق من تعبير منطقي، وتوقف البرنامج فورًا إذا كانت قيمته false
تطبع رسالة تحذير فقط دون إيقاف البرنامج
تُصلح الأخطاء تلقائيًا في الكود

٥. أي مكتبة يجب تضمينها لاستخدام assert؟

iomanip
cassert
algorithm

٦. في مثال مقارنة slow و fast، ماذا يعني الحصول على Time Limit Exceeded؟

على الأرجح أن الصيغة السريعة صحيحة، لكن الحل البطيء يستهلك وقتًا طويلًا على المدخلات الكبيرة
أن هناك بالتأكيد خطأً في الصيغة السريعة
أن البرنامج لن يترجَم (compile) إطلاقًا

٧. أي مما يلي يُعتبر سلوكًا غير معرَّف (Undefined Behavior)؟

الوصول إلى عنصر خارج حدود مصفوفة
استخدام long long بدلًا من int
استخدام setprecision لتنسيق الإخراج

٨. ما الفائدة من "اختبار الضغط" (Stress Testing)؟

مقارنة نتائج حلّك السريع بحلّ بطيء وموثوق للكشف عن اختلافات في النتائج
قياس استهلاك الذاكرة فقط
تسريع البرنامج تلقائيًا

٩. عند حل مسألة متعددة الاختبارات (multiple test cases)، ما الخطأ الشائع الذي يجب الانتباه له؟

نسيان إعادة ضبط المتغيّرات والحاويات بين كل اختبار
استخدام أسماء متغيّرات قصيرة مثل i و j
تضمين مكتبة iostream

١٠. متى يكون "إعادة كتابة الحل من الصفر" خيارًا مناسبًا؟

كملاذ أخير بعد تجربة جميع تقنيات التصحيح الأخرى دون نجاح، مع الاحتفاظ بنسخة من الحل الأصلي
كأول خطوة تُجرّب عند ظهور أي خطأ بسيط
لا يُنصح بها إطلاقًا مهما كانت الظروف

قاموس المصطلحات

Debuggingالتصحيح

عملية اكتشاف سبب سلوك البرنامج غير المتوقع وإصلاحه.

Assertionتأكيد منطقي

شرط يجب أن يكون صحيحًا؛ إن لم يكن كذلك يتوقف البرنامج فورًا (assert).

Undefined Behaviorسلوك غير معرَّف

حالة لا تُحدّد لغة C++ نتيجتها بدقّة، مثل الوصول خارج حدود مصفوفة.

Overflowتجاوز السعة

تجاوز قيمة متغيّر للحدّ الأقصى الذي يستطيع نوعه تخزينه.

Stress Testingاختبار الضغط

مقارنة حل سريع بحل بطيء وموثوق على مدخلات عشوائية كثيرة لإيجاد اختلاف.

Edge Caseحالة حدّية

مدخل غير اعتيادي (كالقيم الصفرية أو القصوى) قد يكشف خللًا في المنطق.

Runtime Errorخطأ أثناء التنفيذ

توقّف البرنامج بشكل غير طبيعي أثناء التشغيل، كفشل assert أو القسمة على صفر.

Time Limit Exceededتجاوز الحد الزمني

الحل صحيح منطقيًا لكنه أبطأ من الحد الزمني المسموح.
