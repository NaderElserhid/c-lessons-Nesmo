# Lesson File Template For Moodle

هذا القالب مُستخرج من تحليل بنية وأسلوب جميع ملفات دروس C++ التي تم إنشاؤها (بنية البرنامج، المتغيرات والأنواع، الثوابت، العوامل، الإدخال/الإخراج، العبارات والتحكم في المسار، عبارة if، حلقة while، حلقة for، الدوال). الهدف: استخراج "طريقة الصناعة" فقط — وليس المحتوى العلمي — بحيث يمكن استخدامه لإنتاج أي درس جديد (C++ أو Python أو غيرهما) بنفس الشكل والجودة والاتساق.

## 1) الهيكل الثابت الكامل للملف (بالترتيب)

كل ملف درس هو صفحة HTML واحدة قائمة بذاتها (HTML + CSS + JS في ملف واحد)، بالترتيب التالي دائماً:

1. **`<head>`**: `lang="ar" dir="rtl"`، عنوان الصفحة بصيغة `TweetKod | <اسم الدرس بالعربية>`، خط Tajawal من Google Fonts، Font Awesome 6.4.0 للأيقونات.
2. **`<style>`**: متغيرات CSS ثابتة (الألوان والظلال)، ثم أنماط: الهيدر، البطاقات (`.card`)، صناديق الكود، صندوق الشرح التفاعلي، صندوق الناتج، القوائم المرقّمة (خطوات)، الجداول، صناديق الملاحظات (تلميح/تحذير/إيجابي)، المحاكيات التفاعلية، شبكة القاموس، الكويز الذاتي.
3. **الهيدر (Header)**: ثابت 100% في كل الملفات — شارة المستوى على اليمين، شعار المنصة واسمها على اليسار.
4. **قسم العنوان (Title section)**: عنوان الدرس (`<h1>`) + سطر نسب واحد ("هذا الشرح مقدم من منصة تويت كود").
5. **سلسلة من "البطاقات" (`.card`)** — كل بطاقة = مفهوم واحد فرعي. هذا هو جسم الدرس (تفصيل كامل في القسم 2 أدناه).
6. **بطاقة "تحقق من فهمك"**: كويز ذاتي تفاعلي (JS)، من 3 إلى 7 أسئلة اختيار من متعدد.
7. **بطاقة "قاموس المصطلحات"**: شبكة مصطلحات إنجليزي/عربي/شرح مختصر.
8. **Footer**: سطر واحد ثابت: "منصة TweetKod — المستوى الأول: لغة C++ للأولمبياد".
9. **`<script>`**: كائن/كائنات `explanations` (شروح الأسطر)، دالة `explainLine`/`copyCode` عامة، دوال المحاكيات الخاصة بالدرس، دالة `checkAnswer` للكويز.

## 2) بنية البطاقة الواحدة (الوحدة الأساسية المتكررة)

كل بطاقة تتبع هذا التسلسل الداخلي (لا تُستخدم كل العناصر في كل بطاقة، لكن الترتيب عند وجودها ثابت):

1. `card-header`: أيقونة Font Awesome + عنوان فرعي (`<h3>`).
2. فقرة تمهيدية قصيرة (2-4 أسطر) تشرح "لماذا" قبل "كيف".
3. صندوق كود (`code-box`) بعنوان ملف وهمي (مثل `main.cpp`)، مع أسطر قابلة للنقر (`code-line`) لعرض شرح كل سطر في `explain-box` أسفله.
4. صندوق الناتج (`output-box`) — أسود مع نص أخضر، يُظهر ناتج التنفيذ المتوقع بالضبط.
5. "مثال إضافي" — مثال ثانٍ أبسط أو بسياق مختلف، دائماً بعد المثال الأساسي مباشرة، بنفس البطاقة غالباً (وليس بطاقة منفصلة) إلا إذا كانت الأمثلة الإضافية كثيرة (عندها تُجمَّع في بطاقة "أمثلة إضافية" مستقلة قرب نهاية الدرس).
6. صندوق ملاحظة عند الحاجة: `tip-box` (تلميح، حدود صفراء متقطعة)، `warn-box` (تحذير، حدود حمراء متقطعة)، `good-box` (ممارسة جيدة/توصية، حدود خضراء متقطعة).
7. جدول (`table-wrap` + `data-table`) عند الحاجة لمقارنة أو تفصيل بنيوي (مثل تفكيك صيغة الكود إلى عناصرها).
8. محاكاة تفاعلية (`sim-box`) عند الحاجة: حقل إدخال + زر تشغيل + منطقة نتيجة/console، تُحدَّث القيم فوراً عبر JS.

# Writing Rules

قواعد إلزامية يجب اتباعها عند كتابة أي ملف درس جديد، بغضّ النظر عن اللغة البرمجية أو الموضوع.

## أ) أسلوب اللغة

- **عربية فصحى ميسّرة**، شبه رسمية، موجّهة مباشرة للطالب (خطاب ضمني بصيغة "نحن نستخدم..." أو "لاحظ أن..." وليس أمراً جافاً ولا عامية).
- كل مصطلح تقني إنجليزي يُكتب **بحروفه اللاتينية الأصلية** (لا يُترجم صوتياً ولا حرفياً)، ويُتبع دائماً بمرادفه العربي بين قوسين عند أول ظهور: مثال: "الثوابت (Constants)".
- الأسماء والدوال والصيغ البرمجية تُكتب دائماً **من اليسار لليمين** داخل عناصر `dir="ltr"` حتى وسط نص عربي (باستخدام `code.inline` أو bidi مناسب)، لتفادي تكسّر الترتيب البصري.
- تجنّب الجمل الطويلة المركّبة؛ الجملة الواحدة تحمل فكرة واحدة.

## ب) طول الفقرات وكثافة المحتوى

- الفقرة التمهيدية لأي بطاقة: **2-4 أسطر كحد أقصى**. لا فقرات طويلة أبداً.
- كل بطاقة (`.card`) تُعالج **مفهوماً فرعياً واحداً فقط**. إذا احتاج الشرح لأكثر من فكرة رئيسية، يُقسَّم إلى بطاقات متعددة.
- عدد البطاقات في الدرس الواحد: عادة بين **6 و12 بطاقة** (بما فيها الكويز والقاموس)، حسب عمق الموضوع.
- عدد الأكواد/الأمثلة داخل الدرس: **مثالان على الأقل لكل مفهوم رئيسي** (المثال الأساسي من المنهج المصدر + مثال إضافي واحد على الأقل بسياق مختلف). المواضيع الغنية (كالدوال أو حلقات التكرار) قد تصل إلى 4-5 أمثلة موزّعة على البطاقات.

## ج) عرض الكود وشرحه سطراً بسطر (القاعدة الأهم)

- كل كود مصدري يُعرض داخل `code-box` بخلفية داكنة (`#1e293b`)، ورأس صغير باسم ملف وهمي (`filename.cpp` / `filename.py`).
- **كل سطر ذو معنى تعليمي** (وليس الأسطر الفارغة أو الأقواس المجردة دائماً) يُغلَّف بـ `<span class="code-line" onclick="...">` قابل للنقر.
- عند النقر، يظهر شرح ذلك السطر تحديداً داخل `explain-box` أسفل الكود مباشرة — **وليس شرحاً تراكمياً للكود كله دفعة واحدة**. هذا هو الفرق الجوهري بين هذا الأسلوب والشرح النصي العادي.
- شروح الأسطر تُخزَّن في كائن JS منفصل (`explanations` أو `EXPLANATIONS`) — **فصل تام بين البيانات (نص الشرح) ومنطق العرض (الدالة العامة `explainLine`)** — بحيث يمكن نسخ نفس منطق العرض لأي درس جديد بدون تعديل.
- الناتج المتوقع يُعرض دائماً بعد الكود مباشرة في `output-box` منفصل (خلفية سوداء، نص أخضر)، بصياغة "الناتج:" قبل الصندوق.

## د) الملاحظات والتنبيهات

ثلاثة أنواع فقط، ولكل نوع لون ودلالة ثابتة عبر كل الدروس:

| النوع | اللون/الحدود | متى يُستخدم |
|---|---|---|
| `tip-box` | أصفر متقطع | تلميح مفيد أو تفصيل يستحق الانتباه، ليس خطأً ولا خطراً |
| `warn-box` | أحمر متقطع | تحذير من خطأ شائع أو سلوك خطير (حلقة لا نهائية، تعديل ثابت...) |
| `good-box` | أخضر متقطع | توصية/ممارسة جيدة أو مقارنة تُفضّل خياراً على آخر |

- **الأخطاء الشائعة** تُدمَج داخل `warn-box` قريباً من الكود الذي يوضّح الخطأ (وليست قسماً منفصلاً بعيداً عن السياق)، غالباً مصحوبة بمقتطف كود خاطئ معلَّق عليه بعبارة مثل "لا تُشغّل هذا الكود فعلياً!".

## هـ) الجداول والقوائم — متى تُستخدم كل واحدة

- **جدول (`data-table`)**: عندما تكون البيانات ثنائية أو ثلاثية الأبعاد بطبيعتها (عنصر ↔ شرح ↔ مثال)، مثل تفكيك صيغة كود، أو مقارنة بين طريقتين، أو جدول لواحق/أنواع.
- **قائمة نقطية (`<ul>`)**: فقط لتعداد شروط أو قواعد قصيرة مستقلة (سطر واحد لكل بند)، مثل "الشرط قد يكون كذا... أو كذا...".
- **قائمة مرقّمة كبطاقات خطوات (`step-item`)**: لتسلسل زمني/منطقي (خطوة 1، 2، 3...) يشرح "كيف يعمل" شيء ما، مع أيقونة رقمية دائرية لكل خطوة.
- لا تُستخدم القوائم أبداً لشرح مفهوم واحد ممتد؛ الشرح المفهومي يبقى نثراً (فقرات قصيرة).

## و) إبراز الكلمات المهمة

- أسماء برمجية (متغيرات، دوال، كلمات مفتاحية) → `<code class="inline">` دائماً، لا نص عادي ولا بولد.
- مصطلح مفهومي جديد يُقدَّم لأول مرة → `<strong>` مرة واحدة عند التعريف، ثم نص عادي بعدها.
- لا إفراط في التلوين أو التغميق؛ العنصر البصري الأهم هو التفاعل (النقر لعرض الشرح) وليس التنسيق الساكن.

## ز) الملخص والواجب/التمرين

- **الخلاصة السريعة**: بطاقة اختيارية قرب نهاية الدرس (قبل الكويز)، عنوانها "خلاصة سريعة"، محتواها 2-4 نقاط `step-item` مختصرة جداً (سطر واحد لكل نقطة) + جملة ختامية تحفيزية واحدة.
- **الكويز الذاتي داخل الصفحة**: 3-7 أسئلة اختيار من متعدد (3 خيارات لكل سؤال عادة)، تصحيح فوري بالألوان (أخضر/أحمر) عبر JS، بدون إعادة تحميل الصفحة.
- **الواجب المنزلي / التمرين اليدوي** (عند الطلب صراحة فقط، ليس في كل درس): بطاقة منفصلة، نص تمرين واضح بجملة أو جملتين، زر "عرض الحل المقترح" يُظهر/يُخفي كود الحل داخل `solution-panel` بأنيميشن ناعم — الحل لا يظهر افتراضياً أبداً.

## ح) القاموس (Glossary) — إلزامي في كل درس

- بطاقة أخيرة قبل الفوتر، عنوانها "قاموس المصطلحات".
- كل بطاقة مصطلح (`term-card`) تحتوي: المصطلح الإنجليزي (LTR، لون أزرق)، المرادف العربي (غامق)، وصف قصير سطر واحد.
- **يجب أن يحتوي القاموس على كل مصطلح إنجليزي ورد في الدرس** ولو مرة واحدة، بدون استثناء.

## ط) التنسيق المناسب للرفع على Moodle

- ملف HTML واحد ذاتي الاكتفاء (CSS وJS داخل نفس الملف) — يُرفع كـ **File resource بوضع Embed**، وليس كـ Page (لأن محرر Page في Moodle يحذف `<script>` والـ `onclick`).
- لا اعتماد على أي مكتبة خارجية غير Google Fonts وFont Awesome (عبر CDN) — لضمان عمل التفاعل حتى لو حُظر الوصول لخدمات أخرى.
- الألوان والخطوط ثابتة عبر متغيرات CSS في `:root` فقط، لضمان اتساق الهوية البصرية (Tweetkod) عبر كل الملفات دون تكرار قيم الألوان يدوياً.

# Python Adaptation

نفس القالب أعلاه يُستخدم **بحذافيره** لأي درس Python، دون أي تغيير في البنية، الترتيب، الأسلوب، الألوان، أو منطق التفاعل. التغيير الوحيد المسموح هو **المحتوى البرمجي والمصطلحات الخاصة باللغة**. تفصيلاً:

## ما الذي يتغيّر

1. **الكود نفسه**: أمثلة C++ (`cout`, `cin`, `int main()`, الأقواس المعقوفة...) تُستبدل بأمثلة Python المكافئة (`print()`, `input()`, لا حاجة لـ `main()` أو أقواس كتلة، الاعتماد على المسافة البادئة (indentation) كبنية للكتلة).
2. **أسماء الملفات الوهمية** في رأس `code-box`: من `example.cpp` إلى `example.py`.
3. **قاموس المصطلحات**: مصطلحات خاصة بلغة Python فقط (مثل: Indentation، List، Dictionary، f-string، بدلاً من: Pointer، Reference، Compile-time...).
4. **صندوق الناتج**: يعكس فعلياً ما يطبعه مفسّر Python (interpreter)، لا المُصرِّف (compiler) — قد يستدعي هذا صياغة مختلفة قليلاً في `warn-box` عند شرح الأخطاء (مثل IndentationError بدل خطأ ترجمة C++ التقليدي).

## ما الذي **لا يتغيّر إطلاقاً**

- ترتيب الأقسام وعدد البطاقات ومنطقها (مقدمة → مفهوم أساسي → تعميق → أمثلة إضافية → ملاحظات → خلاصة → كويز → قاموس).
- آلية "انقر على السطر لعرض شرحه" — تبقى بنفس الكلاس `code-line` ونفس دالة `explainLine` العامة، فقط تُستبدل نصوص كائن `explanations` بشروح مناسبة لكود Python.
- الألوان، الخطوط، الهيدر، الفوتر، شعار المنصة — **بلا أي تعديل** (نفس متغيرات `:root`، نفس رأس الصفحة).
- أسلوب اللغة العربية في الشرح (نفس درجة الرسمية، نفس طول الفقرات، نفس طريقة تقديم المصطلح الإنجليزي بين قوسين).
- منطق الكويز الذاتي وشبكة القاموس والمحاكيات التفاعلية (`sim-box`) — نفس الأنماط والدوال العامة، فقط تُغيَّر البيانات الداخلية (القيم المُدخلة، منطق الحساب) لتناسب مثال Python الجديد.
- قاعدة "لا تظهر الحلول افتراضياً" و"لا نستخدم قوائم لشرح مفهوم ممتد" وكل قواعد قسم Writing Rules أعلاه، بنفس الصرامة.

## خطوات عملية لإنتاج درس Python جديد من هذا القالب

1. انسخ ملف HTML القالب (القسم 1 أعلاه) كاملاً كنقطة بداية.
2. غيّر `<title>` وعنوان `<h1>` فقط إلى اسم درس Python الجديد.
3. لكل بطاقة في منهج Python المصدر (أياً كان)، أنشئ بطاقة `.card` بنفس بنية القسم 2 أعلاه: مقدمة قصيرة → كود Python قابل للنقر → ناتج → مثال إضافي → ملاحظة عند الحاجة.
4. املأ كائن `explanations` بشرح كل سطر كود Python الجديد (نفس الأسلوب: جملة واحدة تشرح ماذا يفعل السطر تحديداً).
