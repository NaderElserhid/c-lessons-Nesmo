CSES 1674 — Subordinates (Tree Algorithms) cses.fi/problemset/task/1674 ↗

Given the structure of a company, your task is to calculate for each employee the number of their subordinates.

Input

The first input line has an integer n: the number of employees. The employees are numbered 1,2,…,n, and employee 1 is the general director of the company.

After this, there are n−1 integers: for each employee 2,3,…,n their direct boss in the company.

Output

Print n integers: for each employee 1,2,…,n the number of their subordinates.

Constraints

1 ≤ n ≤ 2·105

Example
Input:
5
1 1 2 3

Output:
4 1 1 0 0

🗣️ بالعربية — ماذا يعني هذا فعليًا؟

لدى الشركة n موظفًا، والموظف رقم 1 هو المدير العام (الجذر). لكل موظف من 2 إلى n، تُعطى هويّة رئيسه المباشر فقط — وهذا يبني هيكلًا هرميًا بالضبط مثل الشجرة (tree): كل موظف له رئيس مباشر واحد بالضبط، ما عدا المدير العام الذي لا رئيس له. المطلوب: لكل موظف، كم عدد الموظفين الموجودين "تحته" في الهرم — سواء كانوا تابعين له مباشرة، أو تابعين لأحد من يتبعونه، وهكذا (أي كل من في الشجرة الفرعية المتجذّرة عنده، باستثناء هو نفسه).

ترجمة المثال المعطى

الإدخال 1 1 2 3 يعني: رئيس الموظف 2 هو 1، رئيس الموظف 3 هو 1، رئيس الموظف 4 هو 2، رئيس الموظف 5 هو 3. إذن: 1 لديه ابنان مباشران (2 و3)، و2 لديه ابن مباشر واحد (4)، و3 لديه ابن مباشر واحد (5). العدد الإجمالي لمن "تحت" كل موظف: المدير 1 لديه 4 (كل الباقين)، 2 لديه 1 (فقط 4)، 3 لديه 1 (فقط 5)، 4 وَ5 ورقتان بلا مرؤوسين (0 لكل منهما) — بالضبط 4 1 1 0 0.

💡 فكرة الحل: حجم الشجرة الفرعية

هذه المسألة تُترجم مباشرة إلى مفهوم واحد بسيط: عدد مرؤوسي الموظف v = حجم الشجرة الفرعية المتجذّرة عند v، ناقص واحد (لأن v نفسه ليس من ضمن مرؤوسيه).

التعريف الرياضي

size[v] = 1 (نفسه) + مجموع size[child] لكل أبنائه المباشرين.
الإجابة لكل موظف v هي size[v] - 1.

🧭 خطة الحل

  1. اِبنِ قائمة أبناء لكل موظف من مصفوفة "الرئيس المباشر" المُعطاة: لكل i من 2 إلى n، أضف i إلى قائمة أبناء p_i.

  2. شغّل DFS بترتيب post-order بدءًا من المدير العام (1): احسب حجم كل شجرة فرعية بعد حساب أحجام كل الأبناء أولًا.

  3. اطبع size[v] - 1 لكل موظف من 1 إلى n، بنفس الترتيب المطلوب في المسألة.

لماذا post-order تحديدًا؟ لا يمكن حساب size[v] إلا بعد معرفة أحجام كل أبنائه المباشرين أولًا — وpost-order (معالجة الأبناء قبل الأب) يضمن توفر هذه القيم في اللحظة المناسبة تمامًا، بنفس الترتيب الذي استُخدم في مسألة Tree Matching.

🎯 بونص: مقارنة مع Tree Matching — من حالة واحدة إلى حالتين

هذه المسألة تستخدم حالة DP واحدة فقط لكل عقدة (size[v])، لأن السؤال بسيط: "كم شخصًا تحتك؟" — لا يوجد قرار يجب اتخاذه عند كل عقدة، فقط جمع تراكمي. أما في Tree Matching كان يجب تتبّع حالتين (dp0 وdp1) لأن هناك قرارًا حقيقيًا يُتّخذ عند كل عقدة (هل تُطابَق مع أبيها أم لا). هذا نمط عام مفيد: كلما كان القرار عند العقدة يعتمد على شيء خارجها (مثل حالة الأب)، ستحتاج أكثر من حالة DP؛ وكلما كانت النتيجة تراكمية بحتة من الأبناء فقط، حالة واحدة تكفي.

💻 الكود الكامل مع شرح كل جزء

لم يُرفق كود جاهز مع هذه المسألة، لذا الكود التالي من إعدادنا باستخدام الأسلوب القياسي المعروف لحل هذا النوع من المسائل (حجم شجرة فرعية عبر DFS)، وتم التحقق منه يدويًا بالكامل على المثال المُعطى (الناتج طابق 4 1 1 0 0 حرفيًا).

C++ — حل مقترح
#include <iostream>
#include <vector>
using namespace std;

vector<vector<int>> children;
vector<long long> subCount;

void dfs(int v) {
    long long total = 0;

    // احسب كل الأبناء أولًا (post-order)
    for (int c : children[v]) {
        dfs(c);
        total += subCount[c] + 1;   // الابن نفسه + كل مرؤوسيه
    }

    subCount[v] = total;
}

int main() {
    ios::sync_with_stdio(false);
    cin.tie(nullptr);

    int n;
    cin >> n;

    children.assign(n + 1, {});
    for (int i = 2; i <= n; i++) {
        int p;
        cin >> p;
        children[p].push_back(i);
    }

    subCount.assign(n + 1, 0);
    dfs(1);

    for (int i = 1; i <= n; i++) {
        cout << subCount[i] << (i < n ? ' ' : '\n');
    }
    return 0;
}

🔍 شرح مفصّل لكل جزء

vector<vector<int>> children;قائمة أبناء لكل موظف — على عكس Tree Matching حيث كانت قائمة تجاور غير موجّهة، هنا القائمة موجّهة من الأب نحو الأبناء فقط، لأننا نعرف الاتجاه سلفًا من صيغة الإدخال نفسها (كل موظف يعرف رئيسه المباشر).
vector<long long> subCount;مصفوفة النتيجة. القيمة القصوى الممكنة هنا هي n-1 ≤ 2×10^5-1 تقريبًا، وهي تدخل بارتياح شديد في int، لكن long long يظل عادة أمان لا تكلّف شيئًا هنا.
dfs(int v)تأخذ فقط v (بلا حاجة لتمرير الأب p كما في Tree Matching)، لأن قائمة children موجّهة أصلًا ولا يمكن الرجوع منها عن طريق الخطأ نحو الأب.
for (int c : children[v]) { dfs(c); total += subCount[c] + 1; }لكل ابن مباشر: احسب حجم شجرته الفرعية أولًا (recursive call)، ثم أضف "الابن نفسه (+1) + كل مرؤوسيه (subCount[c])" إلى المجموع الكلي عند v.
children.assign(n + 1, {}); قراءة n−1 رقمًالاحظ أن كل الأرقام n−1 تُقرأ من سطر واحد متتالٍ (وليس سطرًا منفصلًا لكل حافة كما في Labyrinth أو Tree Matching) — عامل >> يتجاوز الأسطر الجديدة تلقائيًا فلا فرق عمليًا، لكن يجب الانتباه لصيغة الإدخال هذه بالذات عند اختبار الحل يدويًا.
dfs(1);المدير العام دائمًا هو الموظف رقم 1 حسب نص المسألة صراحة، فلا حاجة لأي بحث عن الجذر كما فعلنا في Tree Matching.
حلقة الطباعة النهائيةتطبع القيم مفصولة بمسافة، مع سطر جديد فقط بعد آخر رقم — مطابقة تمامًا لصيغة الإخراج المطلوبة "اطبع n عددًا صحيحًا" في سطر واحد.

⚗️ المختبر التفاعلي — محسوب المرؤوسين

اكتب التسلسل الهرمي بصيغة الإدخال على CSES بالضبط (n في السطر الأول، ثم سطر واحد يحوي n−1 رقمًا: رئيس كل موظف من 2 إلى n)، أو حمّل مثال المسألة، أو ولّد هرمًا عشوائيًا — ثم اضغط «احسب المرؤوسين». يمكنك أيضًا النقر على أي موظف في الرسم لتظليل كل من يتبعه مباشرة وبشكل غير مباشر، ومشاهدة العدد الدقيق لحالته هو.

القيد الحقيقي على المنصة يصل إلى n ≤ 2×10^5، لكن نُحدّد الحجم هنا بحد أقصى 26 موظفًا فقط لوضوح الرسم — نفس خوارزمية DFS بترتيب post-order تعمل بلا أي تغيير على أي حجم.

📊 تحليل التعقيد ونصائح الحل

الجانبالتعقيدلماذا
الزمنO(n)كل موظف يُزار مرة واحدة بالضبط في DFS، وكل حافة (رئيس→ابن) تُعالَج مرة واحدة أيضًا.
الذاكرةO(n)قائمة children، ومصفوفة subCount، وعمق مكدّس الاستدعاء، كلها خطية في n.

⚠️ أخطاء شائعة عند الحل على المنصة

  1. Stack Overflow على هرم خطي: إن كان كل موظف رئيسًا لموظف واحد فقط بشكل متسلسل (سلسلة طويلة)، فقد يصل عمق DFS التكراري إلى 2×10^5 مستوى. نفس الحل المذكور في مسألة Tree Matching ينطبق هنا: حوّل DFS إلى نسخة تكرارية بمكدّس يدوي (كما في المختبر أعلاه) إن واجهت هذه المشكلة عمليًا.

  2. الخلط في صيغة الإدخال: الأرقام n−1 تُعطى كلها ضمن نفس "الكتلة" من المدخلات (سطر واحد منطقيًا)، بعكس Tree Matching وLabyrinth حيث كانت كل حافة/بيانات في سطر منفصل — لا فرق فعليًا عند القراءة بـcin >> لأنها تتجاوز الأسطر الجديدة تلقائيًا، لكن يجب الانتباه عند اختبار المدخل يدويًا أو كتابته في ملف.

  3. نسيان طباعة كل الـ n قيمة: يجب طباعة عدد مرؤوسي كل موظف من 1 إلى n بما في ذلك المدير العام نفسه والأوراق (التي ستكون قيمتها 0)، وليس فقط الموظفين الذين لديهم مرؤوسون فعليًا.

  4. افتراض ترتيب معيّن للأبناء: ترتيب معالجة الأبناء داخل الحلقة لا يؤثر إطلاقًا على صحة الناتج، لأن العملية جمع تراكمي بحت (commutative) — لا داعِ للقلق بشأن ترتيب إدخال الأبناء في قائمة children.

🚀 مسائل تالية من نفس قسم Tree Algorithms على CSES

بعد إتقان هذه الفكرة الأساسية (حجم الشجرة الفرعية)، القسم نفسه يحتوي: Tree Matching (توسيع الفكرة إلى حالتين DP، كما رأينا في صفحة سابقة)، Tree Diameter وTree Distances I/II (تقنية Re-rooting لحساب معلومات من منظور كل عقدة كجذر)، وCompany Queries I/II (امتداد مباشر لنفس فكرة هذا الهرم الوظيفي، لكن باستعلامات عن السلف على ارتفاع معيّن، ما يتطلب تقنية Binary Lifting). هذا يجعل Subordinates نقطة انطلاق ممتازة قبل تلك المسائل الأكثر تقدّمًا.
