Counting Rooms — عدّ الغرف

مسألة CSES 1192 من قسم Graph Algorithms — عدّ عدد الغرف (المكوّنات المتصلة من خلايا الأرضية) داخل مخطط مبنى، باستخدام نفس فكرة BFS/DFS التي رأيتها في Labyrinth، لكن بهدف مختلف: العدّ بدلًا من إيجاد مسار. هذه الصفحة تجهّزك لفهم نص المسألة كما يظهر تمامًا على المنصة، وتضع بين يديك مختبرًا يكشف كل غرفة بلون مختلف خطوة بخطوة.

📄 نص المسألة كما يظهر على CSES

CSES 1192 — Counting Rooms (Graph Algorithms) cses.fi/problemset/task/1192 ↗

You are given a map of a building, and your task is to count the number of its rooms. The size of the map is n×m squares, and each square is either floor or wall. You can walk left, right, up and down through the floor squares.

Input

The first input line has two integers n and m: the height and width of the map.

Then there are n lines of m characters describing the map. Each character is either . (floor) or # (wall).

Output

Print one integer: the number of rooms.

Constraints

1 ≤ n, m ≤ 1000

Example
Input:
5 8
########
#..#...#
####.#.#
#..#...#
########

Output:
3

🗣️ بالعربية — ماذا يعني هذا فعليًا؟

لديك شبكة n×m، كل خلية فيها إما أرضية . يمكن المشي عليها أو جدار # لا يمكن عبوره. الغرفة هنا تعني بالضبط: مجموعة من خلايا الأرضية المتصلة ببعضها عبر حركات لأعلى/أسفل/يمين/يسار فقط (بدون قطر). المطلوب هو عدّ كم مجموعة منفصلة (متصلة داخليًا لكن غير متصلة مع غيرها) من هذا النوع توجد في الشبكة بأكملها.

ترجمة مباشرة للمصطلح

بلغة نظرية الرسوم البيانية: كل خلية أرضية هي عقدة (node)، وتوجد حافة بين كل خليتين متجاورتين أرضيتين. "الغرفة" هي بالضبط مكوّن متصل (connected component) في هذا الرسم البياني. المسألة إذن تسأل: كم عدد المكوّنات المتصلة الموجودة؟

🎨 عرض المثال المعطى بصريًا

هذا رسم لنفس المخطط من المثال، مع تلوين كل غرفة بلون مختلف بترتيب اكتشافها الطبيعي أثناء مسح الشبكة صفًا صفًا من الأعلى لليسار: الغرفة البرتقالية اكتُشفت أولًا (أعلى اليسار)، ثم الزرقاء (الغرفة الكبيرة المتشعبة)، ثم البنفسجية (أسفل اليسار).

لاحظ كيف أن الغرفة الزرقاء (الوسطى) متشعبة الشكل لكنها لا تزال غرفة واحدة فقط، لأن كل خلاياها متصلة ببعضها عبر مسار من خلايا أرضية متجاورة — الشكل لا يهم، الاتصال هو كل ما يهم.

2

💡 فكرة الحل: عدّ المكوّنات المتصلة

حوّل كل خلية أرضية إلى عقدة في رسم بياني، وأضف حافة بين كل خليتين أرضيتين متجاورتين. المطلوب الآن هو ببساطة: كم عدد المكوّنات المتصلة في هذا الرسم البياني؟

🧭 خطة الحل

  1. امسح الشبكة خلية خلية بترتيب صفوف (من الأعلى لليسار إلى الأسفل لليمين).

  2. كلما وجدت خلية أرضية لم تُزر بعد، فهذا يعني أنك اكتشفت غرفة جديدة لم تُعدّ من قبل — زِد العدّاد rooms بمقدار 1.

  3. ابدأ BFS (أو DFS) من هذه الخلية لتمييز كل الخلايا الأرضية المتصلة بها كـ"مُزارة" — وبذلك لن تُعاد عدّها مرة أخرى لاحقًا في المسح.

  4. تابع المسح حتى نهاية الشبكة. القيمة النهائية لـrooms هي عدد المكوّنات المتصلة، أي عدد الغرف.

هل BFS ضروري هنا، أم يكفي DFS؟ بخلاف Labyrinth (حيث احتجنا BFS تحديدًا لضمان أقصر مسار)، هذه المسألة لا تسأل عن أقصر شيء إطلاقًا — فقط عن الاتصال (connectivity). لذلك BFS وDFS كلاهما صحيح تمامًا وبنفس التعقيد الزمني O(n×m). الكود المعطى يستخدم BFS بقائمة انتظار (queue)، لكن استبدالها بمكدّس (stack) أو باستدعاء ذاتي recursive لتنفيذ DFS يُعطي نفس الإجابة الصحيحة بالضبط.

تشبيه من الحياة الواقعية: هذه بالضبط نفس فكرة أداة "التعبئة بالدلو" (paint bucket / flood fill) في برامج تحرير الصور — عندما تنقر على منطقة بلون معيّن فتمتلئ كل المنطقة المتصلة بنفس اللون تلقائيًا. البرمجية هنا تفعل نفس الشيء: "تملأ" كل غرفة بعلامة "مُزارة" دفعة واحدة.

🎯 بونص: حل بديل باستخدام Union-Find (DSU)

بدلًا من BFS/DFS، يمكن حل هذه المسألة أيضًا بهيكل بيانات Union-Find (Disjoint Set Union): لكل خلية أرضية، اربطها (union) مع جارتها الأرضية اليمنى والسفلية إن وُجدتا، ثم في النهاية عدّ كم "جذرًا" (root) مختلفًا يوجد بين كل الخلايا الأرضية — وهذا العدد هو بالضبط عدد الغرف. هذا الأسلوب مفيد جدًا في مسائل تُضاف فيها الحواف تدريجيًا بمرور الوقت (كأن تُفتح ممرات جديدة لاحقًا)، وهو نمط شائع جدًا يستحق إتقانه بجانب BFS/DFS.

💻 الكود الكامل مع شرح كل جزء

C++ — الحل الكامل
#include <iostream>
#include <vector>
#include <string>
#include <queue>
#include <utility>
using namespace std;

int main() {
    ios::sync_with_stdio(false);
    cin.tie(nullptr);

    int n, m;
    cin >> n >> m;

    vector<string> grid(n);
    for (int i = 0; i < n; i++) cin >> grid[i];

    vector<vector<char>> vis(n, vector<char>(m, 0));
    int rooms = 0;

    const int dr[4] = {-1, 1, 0, 0};
    const int dc[4] = {0, 0, -1, 1};

    for (int i = 0; i < n; i++) {
        for (int j = 0; j < m; j++) {
            if (grid[i][j] != '.' || vis[i][j]) continue;

            rooms++;
            queue<pair<int, int>> q;
            q.push({i, j});
            vis[i][j] = 1;

            while (!q.empty()) {
                auto [r, c] = q.front(); q.pop();

                for (int k = 0; k < 4; k++) {
                    int nr = r + dr[k];
                    int nc = c + dc[k];
                    if (nr < 0 || nr >= n || nc < 0 || nc >= m) continue;
                    if (grid[nr][nc] != '.' || vis[nr][nc]) continue;
                    vis[nr][nc] = 1;
                    q.push({nr, nc});
                }
            }
        }
    }

    cout << rooms << "\n";
    return 0;
}

حلقة for(k=0..3) وفحص الجيران الأربعةلكل جار: تجاوز الحدود أولًا (فحص منفصل)، ثم فحص مدمج (جدار أو مُزارة) قبل تمييزه مُزارًا ودفعه للطابور — نفس نمط التخطي المستخدم أعلاه، مطبّق الآن على كل جار أثناء التوسّع.

مقارنة سريعة مع Labyrinth: لاحظ أن BFS هنا لا يحتاج مصفوفة parDir لإعادة بناء أي مسار — لأننا لا نريد مسارًا، فقط نريد "تغطية" كل الخلايا المتصلة وتمييزها مُزارة. هذا الفرق في الهدف (عدّ/تغطية مقابل أقصر مسار) هو ما يُبسّط الكود هنا مقارنة بمسألة المتاهة.

⚗️ المختبر التفاعلي — عدّاد الغرف بالـ Flood Fill

ارسم مخططك الخاص، أو حمّل مثال المسألة، أو ولّد مخططًا عشوائيًا، ثم اضغط «الغرفة التالية» لمشاهدة الخوارزمية تكتشف الغرف واحدة تلو الأخرى بألوان مختلفة — تمامًا مثل مسح الشبكة صفًا صفًا في الكود الحقيقي أعلاه — أو اضغط «عدّ كل الغرف دفعة واحدة» لإنهاء المسح بالكامل فورًا.

القيود الحقيقية على المنصة تصل إلى 1000×1000 خلية، لكن نُحدّد الحجم هنا (حتى 18×26) للحفاظ على وضوح الرسم والتفاعل السلس — خوارزمية الـ BFS المُنفَّذة هي نفسها تمامًا بغض النظر عن الحجم.

📊 تحليل التعقيد ونصائح الحل

الجانبالتعقيدلماذا
الزمنO(n × m)كل خلية تدخل قائمة الانتظار مرة واحدة فقط على الأكثر (بفضل التحقق من vis قبل الدفع)، وكل خلية تُفحص فيها 4 جيران بزمن ثابت.
الذاكرةO(n × m)مصفوفة الشبكة grid ومصفوفة vis، بالإضافة لقائمة الانتظار التي لا تتجاوز حجمها n×m في أسوأ الحالات.

⚠️ أخطاء شائعة عند الحل على المنصة

  1. استخدام DFS تكراري (recursive) بدلًا من BFS: مع شبكة حتى 1000×1000 = مليون خلية، لو كانت غرفة واحدة ملتوية بشكل يشبه أفعوانًا طويلًا (كممر ضيق متعرّج)، فقد يصل عمق استدعاء DFS التكراري إلى قرابة مليون مستوى، مما قد يُسبب Stack Overflow. الحل المعطى هنا آمن تمامًا لأنه يستخدم BFS بقائمة انتظار (queue) مبنية على الكومة (heap) لا على المكدّس (stack)، لكن لو كتبت DFS بنفسك، اجعله تكراريًا (iterative) بمكدّس يدوي بدلًا من استدعاء ذاتي.

  2. تمييز الخلية "مُزارة" متأخرًا: يجب وضع vis[nr][nc] = 1 فور دفع الخلية إلى الطابور، وليس عند إخراجها لاحقًا — وإلا فقد تُدفع نفس الخلية عدة مرات إلى الطابور من جيران مختلفين، مما يُبطئ التنفيذ (رغم أنه لا يُنتج إجابة خاطئة هنا، فقط عمل زائد غير ضروري).

  3. قراءة بطيئة: نسيان ios::sync_with_stdio(false) مع مليون خلية قد يستهلك وقتًا ثمينًا من حد الثانية الواحدة.

  4. الخلط بين "عدّ الغرف" و"إيجاد مسار": لا حاجة إطلاقًا لمصفوفة dist أو parDir هنا كما في Labyrinth — هذه المسألة تسأل فقط "كم" وليس "كيف تصل"، فلا تُعقّد الحل بإضافة منطق غير مطلوب.

🚀 مسائل تالية من نفس قسم Graph Algorithms على CSES

القسم نفسه يحتوي مسائل تبني تدريجيًا على هذه الفكرة: Labyrinth (نفس فكرة BFS على شبكة، لكن لإيجاد أقصر مسار بدلًا من العدّ)، Building Roads (عدّ المكوّنات المتصلة في رسم بياني عام، ثم ربطها ببعضها بأقل عدد طرق)، Building Teams (BFS/DFS مع تلوين ثنائي للتحقق من رسم بياني ثنائي التجزئة)، وMonsters (BFS متعدد المصادر من نقاط الخطر، مقارنة بمسافة اللاعب). كل هذه المسائل تستخدم نفس عائلة الأدوات (BFS/DFS على الشبكات والرسوم البيانية) بأهداف مختلفة قليلًا في كل مرة.
