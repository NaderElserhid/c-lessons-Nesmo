1. التعريف والمفاهيم الأساسية

الـ Graph هو هيكل رياضي يُستخدم لتمثيل العلاقات بين عناصر منفصلة تُسمّى Vertices (أو Nodes). العلاقة الواحدة بين عنصرين تُسمّى Edge، وهي تعبّر عن ارتباط مباشر بين زوج من الـ Vertices.

رياضيًا يُكتب الـ Graph كـ:

G = (V, E)

حيث V هي مجموعة الـ Vertices، وE هي مجموعة الـ Edges.

مثال واقعي: تخيّل عدة مدن في دولة، بعض أزواج المدن بينهم طرق والبعض الآخر لا. إذا كنت تخطط للسفر من المدينة u إلى المدينة v، قد تحتاج تمرّ على مدينة أو أكثر كمدن وسيطة في الطريق. هذه بالضبط المسألة التي يحلّها الـ Graph! المدن هي الـ Vertices، والطرق المباشرة بينها هي الـ Edges.

لماذا نستخدم Graphs؟

تمثيل المسائل على شكل Graphs يسمح لنا بحلّها بكفاءة باستخدام خوارزميات جاهزة، مثل: BFS لإيجاد أقصر مسار (بعدد الخطوات)، DFS لاستكشاف الرسم البياني بالكامل، Dijkstra للمسارات الأقصر في الرسوم الموزونة، وغيرها الكثير — وهي خوارزميات سنتعلمها في الفصول القادمة.

مختبر تفاعلي: شبكة المدن والطرق

اضغط على أي مدينة لترى جيرانها المباشرين (المدن المرتبطة بها بطريق واحد). أضف مدنًا وطرقًا جديدة بنفسك بالضغط على الأزرار أدناه، ثم شغّل BFS لمشاهدة ترتيب الزيارة خطوة بخطوة انطلاقًا من أول مدينة.

مثال تفاعلي: شبكة المدن والطرق اضغط على أي مدينة لترى مدنًا مرتبطة بها مباشرة (الجيران). يمكنك إضافة مدن وطرق جديدة.

شرح تفاعلي خطوة بخطوة: كيف نبني الـGraph؟

هذا الشرح يعمل مباشرة على نفس شبكة المدن في الأعلى. اضغط "الخطوة التالية ←" لمشاهدة كيف يُبنى الـGraph تدريجيًا، Node تلو الأخرى وEdge تلو الأخرى، مع توضيح ما تغيّر في كل خطوة. بمجرد أن تبدأ الشرح ستُعاد الشبكة أعلاه إلى رسم فارغ لنبنيه معًا من الصفر، ويمكنك دائمًا العودة للشبكة الافتراضية بالضغط على زر "إعادة تعيين" بالأعلى.

2. أنواع الرسوم البيانية

🔀 Undirected Graph

الـ Edges ليس لها اتجاه محدد. إذا كانت هناك علاقة بين u وv، فالعلاقة متبادلة في الاتجاهين. يُشار إليه بمصطلحات مثل bidirectional أو undirected.

➡️ Directed Graph

الـ Edges لها اتجاه محدد. Edge من u إلى v تختلف عن Edge من v إلى u. يُشار إليه بمصطلحات مثل unidirectional أو directed.

⚖️ Weighted Graph

كل Edge لها قيمة (وزن) مرتبطة بها. مثلًا، قد تمثّل المسافة بين المدن أو وقت السفر. الصيغة تُكتب كـ edge(u, v, w) حيث w هو الوزن.

🔗 Weighted + Directed

الأكثر تعقيدًا — الـ Edges لها اتجاه ووزن معًا. شائع في مسائل أقصر مسار مثل Dijkstra أو Bellman-Ford. مثلًا: شبكة طيران بأوقات رحلات محددة الاتجاه.

3. صيغة المدخلات في المسابقات

الطريقة الأكثر شيوعًا لإعطاء الـ Graph في مدخلات المسألة: أولًا نقرأ العددين N وM، حيث N يمثّل عدد الـ Vertices وM عدد الـ Edges. ثم في كل واحد من الأسطر الـ M التالية يُعطى زوج أعداد صحيحة u v (وأحيانًا وزن w). هذا يعني أن هناك Edge بين الـ Vertices u وv. وإذا كان الـ Graph موجّهًا، فعادةً يكون من u إلى v إلا إذا ذُكر غير ذلك.

مثال على مدخلات

input.txt
5 6
1 2
1 3
2 4
3 4
4 5
2 5

  • N=5 vertices، M=6 edges.

  • الأزواج الستة تعني: Edge بين 1↔2، 1↔3، 2↔4، 3↔4، 4↔5، 2↔5.

نصيحة: من أفضل الممارسات أن تجعل كل الحاويات (containers) المتعلقة بالـ Graph معرّفة بشكل global. أغلب خوارزميات الرسوم البيانية يُفضّل تنفيذها باستخدام دوال، ويكون الوصول للـ Graph أسهل بكثير إذا كانت المتغيرات global. مهم جدًا أن تعرف القيود على متغيرات مثل N وM لضبط أحجام الحاويات وتجنّب الوصول خارج الحدود (Out of Bounds).

تحذير: نفترض في هذا الشرح أن الـ Graph لا يحتوي على Multiple Edges، أي لا يوجد زوج من الـ Vertices مرتبطين مباشرةً بأكثر من Edge واحدة. كذلك نفترض عدم وجود Self-loops (وهي Edge من vertex إلى نفسه، مثل edge(3, 3)). بعض المسائل تسمح بهذه الحالات صراحةً، فتأكّد دائمًا من قراءة نص المسألة جيدًا.

4. الاستعلامات الأساسية للمقارنة

قبل أن نختار طريقة التخزين، يجب أن نفهم الاستعلامات التي سنحتاج تنفيذها، لأن كل طريقة لها نقاط قوة وضعف:

  • 📦 التعقيد المكاني: كم مقدار الذاكرة التي تحتاجها هذه الطريقة بالنسبة لـ N وM؟

  • 🔍 هل Edge موجودة؟ ما زمن التحقق من وجود Edge بين vertex رقم u وvertex رقم v؟

  • 🔁 المرور على الجيران: ما زمن المرور على كل الـ Vertices المجاورة لـ v معيّن؟

5. طرق التخزين — 📋 Array of Edges

أبسط طريقة لتخزين الـ Edges. بما أن الـ Edges تُعطى على شكل قائمة أزواج، نخزّنها مباشرةً في array من أزواج. كل عنصر في الـ Array هو زوج (u, v) يمثّل Edge بين vertex رقم u وvertex رقم v.

هذه الطريقة مناسبة عندما نحتاج فقط المرور على كل الـ Edges، مثل خوارزمية Kruskal لإيجاد Minimum Spanning Tree (سنتعلمها لاحقًا).

array_of_edges.cpp
const int maxN = 100'000;
const int maxM = 200'000;
pair<int,int> E[maxM]; // array الـ Edges

int main() {
    int n, m;
    cin >> n >> m;
    for (int i = 0; i < m; i++) {
        int u, v;
        cin >> u >> v;
        E[i] = {u, v}; // نخزّن كل Edge كزوج
    }
}

للـ Weighted Graphs: نعرّف struct يحتوي القيم الثلاث (u, v, w)، أو نستخدم std::tuple أو std::array<int,3>. يُفضّل تجنّب الـ Nested Pairs (مثل pair<pair<int,int>,int>) لأنها تجعل الكود أقل وضوحًا.

التعقيد المكاني (Space)O(M)
التحقق من وجود EdgeO(M)
المرور على جيران VertexO(M)

5. طرق التخزين — 📑 Adjacency List ⭐

الطريقة الأكثر شيوعًا في المسابقات! ننشئ N قوائم، كل واحدة عبارة عن vector، بحيث أن القائمة رقم i تخزن كل الجيران (Neighbors) للـ Vertex رقم i.

هذه الطريقة هي الأمثل لمعظم خوارزميات الرسوم البيانية مثل BFS وDFS والتي تحتاج المرور على جيران كل Vertex.

adjacency_list.cpp
const int maxN = 100'000;
const int maxM = 200'000;

// +1 لأن الـ Vertices غالبًا تبدأ من 1
vector<int> adj[maxN + 1];

int main() {
    int n, m;
    cin >> n >> m;
    for (int i = 0; i < m; i++) {
        int u, v;
        cin >> u >> v;
        adj[u].push_back(v); // أضف v لجيران u
        adj[v].push_back(u); // إذا undirected أضف u لجيران v
    }
}

// للـ Weighted Graphs نستخدم pair:
// vector<pair<int,int>> adj[maxN + 1];
// adj[u].push_back({v, w}); // v الجار ووزنه w
مثال (edges: 1-2, 1-3, 2-4, 3-4, 4-5): adj[1] = { 2 3 } adj[2] = { 1 4 } adj[3] = { 1 4 } adj[4] = { 2 3 5 } adj[5] = { 4 }

مختبر تفاعلي: ابنِ الـ Adjacency List بنفسك

أدخل الـ Edges (كل سطر: u v)

اضغط "بناء الـ Adjacency List" لرؤية النتيجة...

نصيحة التعقيد: رغم أن المرور على جيران Vertex واحد يبدو O(degree)، إلا أنه إذا جمعنا على كل الـ Vertices، فالمجموع الكلي يساوي O(N + M). السبب: كل Edge تُضاف إلى قائمتين بالضبط (جيران طرفيها)، لذا مجموع كل الدرجات (degrees) يساوي 2M دائمًا. تحقّقنا من هذا فعليًا على المثال أعلاه: مجموع أطوال كل القوائم = 2+2+2+3+1 = 10 = 2 × 5.

خطأ شائع: نسيان إضافة الاتجاه الثاني في الرسم غير الموجّه. إذا كتبت adj[u].push_back(v); فقط دون adj[v].push_back(u);، ستحصل على قوائم غير متماثلة (asymmetric) — مثلًا adj[2] ستفتقد الرقم 1 رغم وجود Edge بينهما، مما يكسر أي خوارزمية BFS أو DFS لاحقة بصمت تام.

تحدٍّ للتفكير: هل تقدر تعدّل هذا الـ Container بحيث تسرّع عملية "التحقق من وجود Edge" بدون أن تؤثر كثيرًا على باقي الاستعلامات؟ تلميح: فكّر في استخدام unordered_set بدل vector.

adjacency_set.cpp
vector<unordered_set<int>> adj(maxN + 1);

adj[u].insert(v);
adj[v].insert(u);

bool hasEdge = adj[u].count(v) > 0; // O(1) في المتوسط بدلًا من O(degree)

هذا يحوّل "التحقق من وجود Edge" من O(degree) إلى O(1) في المتوسط، والمرور على الجيران يبقى O(degree) كما هو. الثمن: استهلاك ذاكرة أكبر قليلًا (بنية unordered_set أثقل من vector)، وسرعة فعلية أبطأ قليلًا عند المرور المتكرر بسبب تكلفة الـ hashing — لذا لا تستخدمها إلا إذا كنت فعليًا بحاجة للتحقق المتكرر من وجود Edge.

الاستعلامالتعقيد
التعقيد المكاني (Space)O(N + M)
التحقق من وجود EdgeO(degree(v))
المرور على جيران VertexO(degree(v))

5. طرق التخزين — 🔲 Adjacency Matrix

هذه الطريقة تنشئ مصفوفة بحجم N × N من القيم المنطقية (Booleans)، نسمّيها G، بحيث أن G[u][v] = true إذا كان هناك Edge مباشرة بين u وv، وfalse في غير ذلك.

تتميّز بسرعة التحقق من وجود Edge، لكنها تستهلك ذاكرة كبيرة، لذا تُستخدم فقط عندما يكون N صغيرًا.

adjacency_matrix.cpp
const int maxN = 1'000; // صغير بسبب O(N²) للذاكرة

bool G[maxN + 1][maxN + 1];

int main() {
    int n, m;
    cin >> n >> m;
    for (int i = 0; i < m; i++) {
        int u, v;
        cin >> u >> v;
        G[u][v] = true;
        G[v][u] = true; // إذا undirected
    }
}

// للـ Weighted Graphs:
// int G[maxN+1][maxN+1]; // 0 تعني لا توجد Edge
// G[u][v] = w; // وزن الـ Edge

لماذا لا نستخدمها دائمًا؟ بالنسبة لـ N = 1,000، تحتاج المصفوفة تقريبًا 1 ميجابايت فقط. لكن بالنسبة لـ N = 100,000 (وهو حدّ معتاد في المسابقات)، تحتاج المصفوفة تقريبًا 9.3 غيغابايت — أكبر بكثير من حدّ الذاكرة المعتاد في أي مسابقة! لهذا السبب Adjacency Matrix تصلح فقط عندما تكون N صغيرة.

🔲 Adjacency Matrix: عندما N صغير (حتى ~1000) وتحتاج فحص Edge بسرعة O(1)، أو لخوارزمية Floyd-Warshall (سنتعلمها لاحقًا).

أخطاء شائعة يجب الانتباه لها

1) الترقيم: 0-indexed أم 1-indexed؟

أغلب مسائل المسابقات تُرقّم الـ Vertices من 1 إلى N (1-indexed)، بعكس الأعراف البرمجية المعتادة في المصفوفات (0-indexed). لهذا رأينا في الكود vector<int> adj[maxN + 1]; — الـ +1 هنا ليس اعتباطيًا، بل لضمان أن الفهرس N نفسه صالح (وليس فقط حتى N-1).

2) نسيان الاتجاه الثاني في Undirected Graph

كما رأينا في المختبر التفاعلي، نسيان adj[v].push_back(u); (أو ما يعادله في المصفوفة) يُنتج قوائم جيران غير متماثلة، وهذا يكسر أي خوارزمية لاحقة بصمت دون أي خطأ ترجمة.

3) الخلط بين Directed وUndirected بالخطأ

العكس أيضًا خطأ شائع: إضافة كلا الاتجاهين لرسم بياني يُفترض أنه Directed (مثلًا في مسألة "تبعيات الحزم البرمجية" حيث الحزمة A تعتمد على B، وليس العكس بالضرورة).

4) تجاوز حدود المصفوفة (Out of Bounds)

إذا حجّمت adj[] أو G[][] بحجم أصغر من القيد الفعلي لـ N في المسألة، ستحصل على سلوك غير معرّف (Undefined Behavior) قد لا يظهر كخطأ واضح دائمًا. تحقّق دائمًا من القيود قبل كتابة الكود.

5) استخدام Adjacency Matrix مع N كبيرة

كما رأينا، N = 100,000 مع Adjacency Matrix يحتاج حوالي 9.3 غيغابايت من الذاكرة — سيتسبب هذا في خطأ تجاوز حدّ الذاكرة (Memory Limit Exceeded) فورًا. راجع القيود دائمًا قبل اختيار طريقة التخزين.

نشاط: مراجعة سريعة للمفاهيم الأساسية وأنواع الرسوم البيانية

حدّد إن كانت كل عبارة صحيحة أم خاطئة.

في Undirected Graph، إذا وُجدت علاقة بين u وv فهي متبادلة في الاتجاهين.

في Directed Graph، وجود Edge من u إلى v يعني تلقائيًا وجود Edge من v إلى u.

الصيغة edge(u, v, w) بدون ذكر اتجاه تعني افتراضيًا أن الـ Graph موجّه.

في مدخلات المسابقات، N وM عادةً تمثّلان عدد الـ Vertices وعدد الـ Edges على الترتيب.

نشاط: مراجعة سريعة لطرق التخزين

حدّد إن كانت كل عبارة صحيحة أم خاطئة.

Adjacency List هي الخيار الأمثل لخوارزميات مثل BFS وDFS التي تحتاج المرور على جيران كل Vertex.

مجموع أطوال كل قوائم Adjacency List (لرسم بياني غير موجّه) يساوي دائمًا 2M.

Adjacency Matrix مناسبة دائمًا بغض النظر عن حجم N.

التحقق من وجود Edge في Adjacency Matrix يكلّف O(1).

خلاصة سريعة

Graph = (V, E): مجموعة Vertices ومجموعة Edges تربطها.
أربعة أنواع أساسية: Undirected، Directed، Weighted، Weighted+Directed.
ثلاث طرق تخزين: Array of Edges (للمرور الكامل)، Adjacency List (الأكثر استخدامًا)، Adjacency Matrix (لـ N الصغيرة أو فحص Edge السريع).
انتبه دائمًا لـ: الترقيم (0 أم 1)، اتجاه الـ Edges، حدود N وM، وحجم الذاكرة قبل اختيار الطريقة.

تمارين منزلية

1) ابنِ Adjacency List يدويًا

لديك رسم بياني غير موجّه بالـ Edges التالية: (1,2), (2,3), (1,4), (3,4), (4,5), (2,5). اكتب adj[i] لكل i من 1 إلى 5.

adj[1] = { 2 4 } adj[2] = { 1 3 5 } adj[3] = { 2 4 } adj[4] = { 1 3 5 } adj[5] = { 4 2 }

تحقّق: مجموع الأطوال = 2+3+2+3+2 = 12 = 2 × 6 (عدد الـ Edges). ✓

2) احسب الذاكرة اللازمة

لديك رسم بياني بـ N = 2,000 vertex. كم ميجابايت تقريبًا تحتاجها Adjacency Matrix من نوع bool (بايت واحد لكل خلية)؟

2000 × 2000 = 4,000,000 بايت ≈ 3.8 ميجابايت

هذا الحجم مقبول تمامًا (على عكس N=100,000 التي رأيناها سابقًا تحتاج ~9.3 غيغابايت) — لهذا Adjacency Matrix تصلح جيدًا عندما N في حدود الآلاف فقط.

3) اختر طريقة التخزين المناسبة

لكل سيناريو التالي، اختر طريقة التخزين الأنسب (Array of Edges / Adjacency List / Adjacency Matrix) مع تبرير مختصر:

  • (أ) رسم بياني بـ N=50 فقط، وتحتاج فحص "هل يوجد طريق مباشر بين المدينتين X وY؟" آلاف المرات.

  • (ب) رسم بياني بـ N=10⁵ وM=2×10⁵، وتحتاج تنفيذ BFS لإيجاد أقصر مسار.

  • (ج) رسم بياني بـ N=10⁵ وM=2×10⁵، وتحتاج فقط ترتيب كل الـ Edges حسب الوزن (لخوارزمية Kruskal).

(أ) Adjacency Matrix: N صغيرة جدًا (50)، والاستعلام المتكرر هو "فحص وجود Edge" — بالضبط ما تتفوق فيه المصفوفة بزمن O(1).

(ب) Adjacency List: N وM كبيرتان، وBFS يحتاج المرور المتكرر على جيران كل Vertex — تمامًا استخدام Adjacency List النموذجي.

(ج) Array of Edges: لا نحتاج أي استعلام عن الجيران أو وجود Edge، فقط قائمة كل الـ Edges لفرزها — هذا بالضبط ما تحتاجه Kruskal.

قاموس المصطلحات

Graphرسم بياني

هيكل رياضي G=(V,E) يمثّل علاقات بين عناصر (Vertices) عبر روابط (Edges).

Vertex (Node)رأس / عقدة

عنصر أساسي واحد في الرسم البياني.

Edgeحافة / رابط

ارتباط مباشر بين زوج من الـ Vertices.

Degreeدرجة العقدة

عدد الـ Edges المرتبطة مباشرة بـ vertex معيّن.

Undirected / Directedغير موجّه / موجّه

هل للـ Edge اتجاه محدد أم أنها متبادلة تلقائيًا.

Weighted Graphرسم بياني موزون

رسم بياني تحمل فيه كل Edge قيمة (وزن) مرتبطة بها.

Adjacency Listقائمة الجوار

تخزين جيران كل vertex في قائمة منفصلة؛ الطريقة الأشيع في المسابقات.

Adjacency Matrixمصفوفة الجوار

مصفوفة N×N تحدد مباشرة وجود Edge بين كل زوج من الـ Vertices.

Multiple Edgesحواف متعددة

أكثر من Edge واحدة تربط نفس زوج الـ Vertices.

Self-loopحلقة ذاتية

Edge تربط vertex بنفسه.

BFS (Breadth-First Search)البحث بالعرض

خوارزمية مرور تستكشف الرسم البياني مستوى تلو الآخر، بدءًا من نقطة انطلاق؛ سنتعلّمها بالتفصيل في الفصل القادم.
